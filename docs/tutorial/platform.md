# 在 SDK 之上构建开源 Agent 管理平台

[教程目录](README.md) · [远程服务教程](08-server.md)

## 平台的核心职责

平台回答“谁可以在哪个项目中使用哪个 Agent 执行什么任务”，SDK 回答“一次运行如何调用模型、执行工具并留下结果”。保留这个边界，后续才能管理多个项目、多个 Worker，甚至接入不同 Agent 引擎。

平台是下一阶段项目，本轮不实现前端或用户系统。主线教程需要提前确定的只是 SDK 生命周期、事件和工作区协议。

## 领域对象

| 对象 | 保存什么 | 不应混淆的关系 |
| --- | --- | --- |
| Project | 仓库、默认分支、项目配置 | 一个项目可以有多个工作区 |
| AgentProfile | 模型配置引用、提示词、工具、策略版本 | 配置可复用，会话历史不可共享 |
| Conversation | 连续交互与事件历史 | 一个会话包含多个 Run |
| Run | 一次执行、状态、预算、结果 | 每次执行有独立 ID |
| Workspace | 代码目录或容器、资源限制 | 生命周期可以超过一次 Run |
| Worker | 任务执行节点与健康状态 | Worker 不是用户，也不是 Agent 配置 |
| Artifact | 补丁、日志、测试报告、生成文件 | 内容存储与访问授权分离 |

不要从第一版就建立复杂组织层级，但存储与 API 中要能追踪资源所有者，后续授权不能只依赖 URL 不易猜。

## 平台最小版本

第一轮先做到：创建项目、选择 Agent 配置、提交任务、查看事件与文件差异、处理确认、取消运行、继续会话。所有按钮必须落到 SDK 或 Agent Server 已定义的操作，不在前端拼接隐藏的 shell 指令。

第二轮增加队列与 Worker：并发限额、领取租约、心跳、超时回收、排队状态。`queued` 是平台调度状态；SDK 的运行生命周期从 Worker 开始执行后进入 running，两层状态映射要明确。

第三轮增加团队能力：项目授权、密钥托管、资源配额、审计和独立工作区。跨用户使用同一路径不是隔离；同一个 Git 分支也不是隔离。

## 服务端不能简单重试整个任务

Worker 丢失心跳后，应先确认原 Worker 已停止或使用 fencing token 拒绝旧持有者继续执行，再决定恢复。租约过期并不自动停止旧进程。如果两个 Worker 都在同一目录修改代码，事件数据库的唯一约束也无法撤销文件副作用。

平台任务重试需要引用原 run_id 并创建新的尝试记录；先恢复未知动作状态，再决定是否启动新执行。禁止以“HTTP 超时”为由无条件重发命令。

## 未来管理其他 Agent

优先让自研 SDK 的流程跑通。需要接入外部 Agent 时，在平台边界定义 AgentBackend：启动、发送消息、取消、读取事件、列出能力。外部 Agent 通过适配器接入，不把它们的进程管理塞进核心推理循环。

能力要显式声明，例如是否支持确认、恢复、文件差异、事件游标。不能将不支持暂停的引擎包装成“暂停成功”。ACP 等现有协议可在这一层评估，具体兼容性以实际实现为准。

## 第一版刻意保留的空白

多 Agent 调度、插件市场、浏览器桌面、定时自动化、复杂知识库和 Kubernetes 运维留到基本平台稳定后推进。它们是扩展方向，不应成为本地 SDK 发布的前置条件。

平台开工门槛：独立 SDK 安装通过、同会话并发受控、取消可确认、事件可回放、工作区可隔离、远程重复请求不双执行。验收详见 [逐章清单](acceptance.md)。
