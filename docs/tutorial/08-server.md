# 进阶章 用远程服务连接未来管理平台

[上一章](07-sdk-cli.md) · [目录](README.md) · [平台规划](platform.md)

## 从函数调用变成远程任务

管理平台需要启动任务、查看进度、处理确认和请求取消。它不应该通过启动 CLI 再解析终端输出实现这些能力。本章新增独立 `e-agent-server` 包，将第七章的 SDK 接口映射为网络协议。

先做单用户、单 Worker 的开发服务，建议用 FastAPI 生成 OpenAPI 契约。下文接口是本项目的设计，不是 OpenHands 现成端点的复制。多用户发布前需要完成平台章节中的身份与资源隔离。

## HTTP 请求不拥有 Run

创建运行的请求应快速返回 `202` 与 `run_id`，后台 Worker 持有实际运行任务。浏览器断开只停止事件读取，不取消执行；明确调用取消接口才停止 Run。

服务中设置 ConversationManager，负责会话对象缓存、活动任务表和事件存储。单进程版在创建任务前持有会话锁，拒绝同会话重复运行。对象字典只保存活动对象，历史记录查询必须来自持久化存储。

API 层、任务管理器和 SDK 的调用顺序如下：

```text
POST run
  → 认证并查找会话
  → 检查 Idempotency-Key
  → 持久化运行请求
  → Worker 领取并调用 Conversation.run()
  → SDK 持久化事件
  → GET events 返回增量
```

开发版可以使用进程内调度，但启动时必须扫描未完成记录，不能因为内存任务表丢失就把它们显示成成功。平台版再加入持久队列、租约和心跳。

## 最小 API 契约

| 方法与路径 | 请求 | 响应与行为 |
| --- | --- | --- |
| `POST /v1/conversations` | agent 配置引用、workspace 配置引用 | `201`，conversation_id |
| `GET /v1/conversations/{id}` | 无 | 会话元数据与当前状态 |
| `POST /v1/conversations/{id}/runs` | prompt，Idempotency-Key 请求头 | `202`，run_id；会话忙时 `409` |
| `GET /v1/runs/{run_id}` | 无 | 当前状态、结果摘要、用量 |
| `POST /v1/runs/{run_id}/cancel` | 无 | 取消请求已接受；客户端继续读取最终状态 |
| `GET /v1/conversations/{id}/events?after_seq=0&limit=100` | 游标与页大小 | 有序事件、next_seq、has_more |
| `POST /v1/conversations/{id}/confirmations/{confirmation_id}` | approve 或 deny | 仅允许处理绑定到该会话的有效动作 |

相同调用者、会话和 Idempotency-Key 的相同请求返回同一 run_id；相同键但不同内容返回冲突。取消已终止的 Run 是幂等操作，不能创建新 Run。

`run_id` 应由任务接收层分配并传给 SDK 内部启动方法；公共本地 `run(prompt)` 仍可自行生成 ID。不要让 HTTP 任务 ID 与 SDK 事件中的 run_id 各生成一份。

接口不接受任意宿主机绝对路径。客户端提交平台认可的 workspace 配置引用，由服务端解析成实际执行环境。即使只做单用户开发服务，也应默认绑定回环地址并使用开发令牌。

## 先轮询事件 再做实时连接

第一版按 `after_seq` 轮询持久化事件。页面记住最后一个 seq，断线后继续查询即可。这样能先证明恢复语义，不必同时实现 WebSocket 的订阅与重连。

后续 SSE 或 WebSocket 只是事件传输方式，仍使用相同事件信封。建立实时连接时需要解决“读历史”和“订阅新事件”之间的竞态，可采用持久日志追尾或先订阅缓冲、再回补历史并按 seq 去重。

慢客户端不能堵住 Agent 的持久化路径；客户端缓冲必须有上限，超限后关闭连接并要求按游标恢复。模型 token 增量可以作为临时 UI 事件传输，持久化完整 assistant 消息仍是恢复依据。

## 把 Workspace 换成容器

保持第四章 Workspace 协议不变，新增 DockerWorkspace。教学版选择：Agent 与模型适配器在服务端 Worker 中运行，代码工具在每个 Workspace 的独立容器中执行。模型凭据因此无需注入代码执行容器。

容器生命周期必须包括创建、就绪检查、执行、取消、关闭和异常回收。服务端持有 workspace_id 到容器 ID 的映射；平台只能引用 workspace_id，不能自行提交任意容器命令。

实现步骤：

1. 构建只包含练习项目所需解释器与工具的镜像，固定镜像版本或摘要。
2. 为会话分配独立目录或卷，仅挂载该工作区，不挂载整个用户目录或 Docker socket。
3. 使用非 root 用户，限制内存、CPU、进程数，配置网络策略与可写目录。
4. 通过受控文件接口与 exec 接口实现 Workspace 协议；保留退出码、截断和超时语义。
5. 取消时确认容器内活动操作停止；无法确定时关闭整个工作区执行容器。
6. 在异常退出和服务重启时，根据持久化映射回收孤立容器。

Docker 本身不等于完整多租户安全方案；平台阶段还需要按部署环境确定隔离级别、密钥注入方式和网络授权。这里只验证“相同 Agent 配置可以更换执行环境”。

## 远程恢复的额外约束

网络超时可能表示“请求未到达”，也可能表示“动作执行了但响应丢失”。调用者不能据此重复写文件或重跑命令。远程执行协议使用动作键 `(run_id, turn, call_id)`，执行端保存开始与完成记录；查询结果未知时进入 outcome_unknown 流程。

Workspace 的寿命与 Run 不同：一段会话的下一次运行可能还需要上次文件。不要在每次 Run 结束时无条件删除工作区；由会话关闭策略或平台回收策略管理，并区分运行日志保留与文件保留。

## 本章验收

使用相同模型脚本与练习仓库分别通过本地 SDK 和 HTTP 服务执行，比较最终文件及关键事件顺序。浏览器断开后任务继续；重连无事件缺口；重复提交不产生双执行；取消后工作区无活动命令；服务崩溃后未完成任务显示 interrupted。

先通过这些验收，再为服务添加真正的管理平台。漂亮的任务页面无法弥补重复执行、恢复丢失或会话串用。
